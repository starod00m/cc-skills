Post-completion finalize step. Rebase your commits onto the latest target branch and organize them for merge.

Target branch: $ARGUMENTS (if not specified, use "main")

Steps:

1. Fetch latest changes: run `git fetch origin`

2. **Создать бекап-ветку** перед любыми изменениями истории:
   - Run: `git branch backup/<current-branch-name>-$(date +%Y%m%d-%H%M%S)`
   - Вывести имя бекап-ветки пользователю

3. Rebase onto target branch:
   - Run: `git rebase origin/<target-branch>`
   - Конфликты — `Skill(resolving-merge-conflicts)`: разбор по ханкам, намерение каждой стороны
     прослеживается до первоисточника (сообщение коммита, MR, тикет), затем `git rebase --continue`.
     Скилл доводит ребейз до конца и `--abort` не делает
   - Скилл разобрал не все ханки — `git rebase --abort`, бекап-ветка из шага 2 остаётся, и сообщить,
     на чём встали

4. Решить группировку коммитов **самостоятельно** на основе логического разбиения. **Это всегда так — никогда не спрашивать пользователя про группировку.** Цель скилла фиксирована и не обсуждается в каждом запуске: получить чистую историю, сгруппированную по логическим частям работы над фичей. Не спрашивать «нужна ли чистая история», «делать 1, 2 или N коммитов», «как сгруппировать» — это решение целиком на агенте и следует из содержимого коммитов и diff'ов, а не из мнения пользователя. Количество коммитов агент определяет сам: **минимально достаточное** для выполнения принципа логического разбиения — не больше, чем требуется, чтобы разделить логически разные блоки:
   - Run: `git log origin/<target-branch>..HEAD --oneline`
   - При необходимости посмотреть `git show <hash>` или `git diff` между коммитами, чтобы понять что в них реально лежит
   - **Принцип:** один логический блок работы = один коммит. Логический блок определяется по **сущности/области, над которой шла работа**, а не по типу изменения. Если работа шла над одной сущностью — это один коммит, даже если внутри есть и реализация, и тест, и обновление документации, и правка конфига к ней. Дробить один логический блок по типам изменений (отдельно код, отдельно тесты, отдельно доку) **не нужно** — это та же работа над одной сущностью.
   - **Финальная история должна выглядеть так, будто всё сделали правильно с первого раза**, без следов итераций по ревью и промежуточных шагов. Читающий историю не должен видеть, что был code review, были правки, были возвраты — только чистые логические коммиты конечного результата.
   - **Схлопывать (fixup в родительский коммит)** — обязательно, не на усмотрение:
     - **Коммиты с правками по code review** ("fix: правки по ревью", "правки по ревью", "исправления по code review", "fix: замечания ревьюера", "правки после ревью", "итерация N по ревью" и т.п.) → **fixup в тот feat/исходный коммит, к которому эти правки относятся.** Правки по ревью не должны существовать как отдельные коммиты — они вливаются в коммит фичи так, будто фича сразу была написана с учётом этих правок. Если правки по ревью затрагивают несколько исходных коммитов — распределить их по соответствующим родительским коммитам (через `git rebase -i` с переносом fixup-строк к нужным родителям).
     - "wip", "tmp", "промежуточный коммит" → fixup
     - Коммиты с одинаковым или почти одинаковым смыслом → squash/fixup
     - Мелкие правки (опечатки, форматирование, import) к предыдущему коммиту → fixup
     - Реализация фичи (или её части) + тест к ней + обновление документации/конфига по той же сущности → **один коммит** (это одна логическая работа, дробить не надо)
   - **Оставлять отдельными** только коммиты с действительно разной логической сутью / над разными сущностями: например, "feat: добавить API эндпоинт" и "refactor: выделить не связанный с эндпоинтом общий helper" — это два разных блока. Сомневаешься, одна это сущность или две — склоняйся к объединению (меньше коммитов лучше, пока они логически связны).
   - Кратко вывести **решение** (не «план на согласование»): какие коммиты схлопываются и куда, какие остаются, и итоговые сообщения. Сразу переходить к шагу 5 без ожидания подтверждения

5. Применить группировку через `git rebase -i origin/<target-branch>`:
   - Использовать fixup (не squash) для коммитов-правок, чтобы не засорять сообщение
   - **Правки по ревью** ставить fixup-ом и при необходимости переносить fixup-строку вверх/вниз в todo-листе rebase так, чтобы она шла сразу после своего родительского feat-коммита — тогда правка вольётся именно в коммит фичи, а не останется висеть отдельно
   - Для итоговых коммитов — reword если сообщение нужно улучшить
   - Если после группировки остался всего 1 коммит — это нормально, так и должно быть

6. **Верификация: сравнить с бекапом** что ничего не потерялось:
   - Run: `git diff backup/<backup-branch-name>..HEAD`
   - Если diff пустой — всё ок, история переписана без потерь
   - Если diff НЕ пустой — **СТОП**. Вывести diff, объяснить что именно отличается, спросить пользователя как поступить. При необходимости восстановить из бекапа: `git reset --hard backup/<backup-branch-name>`

7. **Шаг «доки» — сверка документации с состоянием ПОСЛЕ мержа.** Ветка умирает при мерже, поэтому это последняя дешёвая точка, где доку можно поправить одним коммитом, а не догоняющим MR.

   Что делать:
   - Собрать документные файлы итогового diff:
     ```bash
     git diff origin/<target-branch>...HEAD --stat -- '*.md' 'docs/**' 'README*' 'CLAUDE.md'
     ```
   - Прочитать **добавленные** строки этих файлов (`git diff origin/<target-branch>...HEAD -- <файл>`) и найти утверждения, которые мерж делает ложными:
     - переходное обрамление: «пока», «сейчас выключено», «ещё не», «будет», «нужно будет», «после деплоя», «once deployed», «to enable»;
     - инструкции по включению внутри доки: «чтобы включить — поставь флаг / прогони миграцию / выкати» (это материал рунбука, не коммитируемой доки);
     - описание состояния **до** изменения там, где MR это состояние меняет.
   - Отдельно — доки, которых в diff **нет**, хотя MR меняет описанное в них поведение: пользовательские страницы, README, `CLAUDE.md`. Отсутствие файла в diff — не доказательство того, что он актуален.

   **Граница:** сверяем состояние **кода и конфига** после мержа, а не рантайма. «Версия 0.8.0, канал в карте каналов» — правда сразу после мержа, так и должно быть написано. «Выкачено в кластер и принято» — рантайм, в момент мержа ещё неправда: такие факты в коммитируемую доку не идут, им место в `## Лог работы` доки тикета постфактум.

   Найденное **не чинить молча**: вывести списком `файл:строка → что утверждает → как должно звучать` и спросить пользователя (применить / оставить осознанно с причиной). Ничего не найдено — так и сказать одной строкой: это вердикт, которым в доке тикета закрывается обязательный пункт «доки описывают состояние ПОСЛЕ мержа» (см. `st-ticket-workflow`).

8. Verify the branch is ready:
   - Run tests using the project's test command (check CLAUDE.md or plan file for the correct command)
   - Run linter if applicable

9. **Ссылка на MR — обязательный вывод.** В конце всегда искать существующий MR для текущей ветки и выводить кликабельную ссылку на него:
   - Run: `glab mr list --source-branch "$(git branch --show-current)"`
   - Если MR найден — вывести его **полный кликабельный URL** (`web_url`, вида `https://.../-/merge_requests/<iid>`), а не только номер. В терминале кликабелен именно полный `https://`-URL, поэтому печатать URL целиком.
   - **Предупреждение о рассинхроне:** этот скилл переписал историю (rebase/группировка), но НЕ пушил. Значит найденный MR показывает **старую** историю ветки до синхронизации с удалёнкой. Явно предупредить, что для отражения переписанной истории в MR нужен force-push (`git push --force-with-lease`).
   - Если MR **не найден** — явно написать «MR для ветки не найден» и предложить создать его через `/st-mr-create`. Ссылку на форму создания нового MR не выводить.

10. Report:
   - Что было: количество коммитов до
   - Что стало: количество коммитов после, их список
   - Имя бекап-ветки (на случай если нужно откатить)
   - Результат верификации (diff пустой / не пустой)
   - **Вердикт шага «доки»** (из шага 7) — либо «расхождений нет», либо список найденного. Этой строкой в доке тикета закрывается обязательный пункт «доки описывают состояние ПОСЛЕ мержа», поэтому она обязана быть в отчёте всегда.
   - **Кликабельная ссылка на MR** (из шага 9) — либо URL существующего MR с предупреждением о рассинхроне, либо пометка «MR не найден, создать через /st-mr-create»

This step is best-effort - if rebase fails, explain why and the branch remains as-is.
