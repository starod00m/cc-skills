# st-mr-create: Создание Merge Request в GitLab

Цель: провести пользователя от текущего состояния ветки до готового MR с минимумом шагов.

## Параметры

- `$ARGUMENTS` — целевая ветка и флаги (например `--draft`)
- Парсинг: если аргумент начинается с `--`, это флаг. Если это имя ветки — целевая ветка.

```
TARGET_BRANCH = первое слово $ARGUMENTS без `--`, если не указано — определить автоматически (см. ниже)
IS_DRAFT = true, если `--draft` есть в $ARGUMENTS
```

### Определение TARGET_BRANCH по умолчанию

**Нет единого дефолта.** В разных репозиториях дефолтная ветка разная (`master`, `main`, `develop`), поэтому её нельзя хардкодить — надо определять из самого репозитория. Каскад (первый успех выигрывает):

1. **Пользователь передал имя ветки в `$ARGUMENTS`** — используй его, автоопределение не запускай.
2. **Локальный кэш (без сети, мгновенно):**
   ```bash
   git symbolic-ref refs/remotes/origin/HEAD --short 2>/dev/null | sed 's@^origin/@@'
   ```
   Если вернулось непустое имя — это `TARGET_BRANCH`.
3. **Если шаг 2 пуст** (`origin/HEAD` не настроен локально — частый случай после `git clone`), спроси remote и закэшируй результат:
   ```bash
   git remote set-head origin --auto >/dev/null 2>&1
   git symbolic-ref refs/remotes/origin/HEAD --short 2>/dev/null | sed 's@^origin/@@'
   ```
   `set-head --auto` пишет `origin/HEAD` в `.git/refs` — на следующем запуске сработает уже быстрый шаг 2.
4. **Если и это пусто** (нет сети, remote недоступен) — не угадывай. Сообщи пользователю, что не удалось определить дефолтную ветку, и спроси её явно через `AskUserQuestion`.

Полученное значение сохрани в `TARGET_BRANCH` и используй во всех дальнейших шагах.

## Шаг 0: Сбор состояния

Параллельно выполни:

```bash
git branch --show-current          # текущая ветка
git status --short                  # unstaged/staged файлы
git log --oneline -10               # последние коммиты
git remote -v                       # наличие remote
```

Также получи имя текущего пользователя GitLab (работает в контексте git-репозитория):

```bash
glab api /user
```

Извлеки поле `username` из JSON-ответа: `glab api /user | python3 -c "import sys,json; print(json.load(sys.stdin)['username'])"`

**Важно:** `CURRENT_USER` берётся ТОЛЬКО из вывода этой команды. Не придумывай username из контекста — всегда выполняй команду и используй реальное значение.

Сохрани: `CURRENT_BRANCH`, `CURRENT_USER` (поле `username`), список изменённых файлов.

**Если remote не настроен** — сообщи пользователю и остановись.

## Шаг 1: Предложить финализацию ветки

Если `CURRENT_BRANCH` == `main` или `master` или `develop`:

> ⚠️ Ты на ветке `{CURRENT_BRANCH}`. Для MR нужна отдельная ветка. Укажи имя новой ветки:

Задай через `AskUserQuestion`:
- Вопрос: "Ты на основной ветке. Введи имя новой feature-ветки для MR (или Other)"
- Header: "Имя ветки"
- Options: предложи автогенерацию из последнего коммита

Если пользователь указал имя — выполни:
```bash
git checkout -b <имя ветки>
```

---

Если ветка нормальная (не основная) — финализация **обязательна и выполняется без вопроса пользователю**. Сразу вызови:

```
Skill tool: st-branch-finalize
args: TARGET_BRANCH
```

Не спрашивай через `AskUserQuestion`, нужна ли финализация — она всегда выполняется как часть цикла создания MR (rebase на {TARGET_BRANCH} + чистка истории коммитов).

После финализации продолжи со Шага 2.

## Шаг 2: Коммит связанных изменений

Если в `git status --short` есть unstaged или staged изменения:

Покажи список изменённых файлов и спроси:

```
AskUserQuestion:
  question: "Есть незакоммиченные изменения. Что с ними делать?"
  header: "Unstaged файлы"
  options:
    - "Закоммитить всё — добавить все файлы и создать коммит" (Recommended)
    - "Выбрать файлы — укажи в Other какие файлы включить"
    - "Пропустить — создать MR без коммита этих изменений"
    - "Stash — отложить изменения через git stash"
```

Если выбрано "Закоммитить всё":
1. Сгенерируй описание коммита на основе изменённых файлов и diff (кратко, на русском — конвенция-пример, замени на свою).
2. Выполни:
   ```bash
   git add <список конкретных файлов>
   git commit -m "$(cat <<'EOF'
   <сгенерированное описание>
   EOF
   )"
   ```
3. Проверь `git log -1` — коммит создан успешно.
4. Если pre-commit хук упал — исправь проблемы и создай НОВЫЙ коммит (не --amend).

Если "Выбрать файлы" — пользователь укажет файлы в Other, добавь только их.

Если "Stash" — выполни `git stash`.

## Шаг 3: Push ветки

```bash
git push -u origin HEAD
```

Если push упал из-за "rejected" (non-fast-forward) — спроси пользователя:

```
AskUserQuestion:
  question: "Push отклонён (remote опережает). Как поступить?"
  header: "Конфликт push"
  options:
    - "Force push — перезаписать remote ветку (git push --force-with-lease)"
    - "Отмена — разберусь сам"
```

Force push выполняй только если пользователь явно выбрал этот вариант.

## Шаг 4: Формирование описания MR

### Принцип: описываем итоговое состояние ветки, а не путь к нему

MR — это предложение влить в `TARGET_BRANCH` **итоговый diff**. Ревьюер смотрит на конечное состояние кода, а не на то, как автор к нему пришёл. Поэтому описание строится **только из итогового diff** ветки против target, а не из истории коммитов.

Почему это важно: внутри ветки нормально, что подход эволюционирует — в одном коммите ввели решение, в следующем переделали, в третьем выкинули. Если описание MR пересказывает коммиты, оно отражает эту эволюцию ("добавили X", "заменили X на Y", "убрали X") — а ревьюеру это бесполезно и сбивает с толку. В итоговом diff осталось только Y — про него и пишем.

### Что читать

Источник истины — **только** эти команды:

```bash
git diff origin/{TARGET_BRANCH}...HEAD          # полный diff ветки против target
git diff origin/{TARGET_BRANCH}...HEAD --stat   # обзор затронутых файлов
```

Тройные точки `...` критичны: это diff от точки развилки, без посторонних изменений из target.

**Не читай** `git log` для формирования описания. Сообщения промежуточных коммитов не должны попадать в MR ни в каком виде — даже как «вдохновение» для формулировок. Если автор в коммитах писал «добавил кэш» → «переделал кэш на Redis» → «убрал кэш совсем», в итоговом diff кэша нет, и в описании MR его быть не должно. Чтение `git log` создаёт соблазн пересказать процесс — поэтому проще его не читать вообще.

Единственное исключение — если diff пустой или подозрительно мал (например, всё откатили к target), тогда `git log` нужен, чтобы понять, что вообще предлагается мержить, и сообщить пользователю.

### Заголовок MR

Формат заголовка **всегда** стандартизирован (это конвенция нашей команды — пример; замени на принятую у себя):

```
[КЛЮЧ-ТИКЕТА] короткое описание
```

Пример: `[PROJ-123] Вход по одноразовому коду из письма`.

- **Ключ тикета в квадратных скобках — обязателен.** Обычно ты уже знаешь его из контекста: работа велась через другие скиллы (`/st-ticket-workflow`, `/st-plan-create`), имя ветки чаще всего содержит ключ (например `feature/proj-123-add-login`), в `docs/tickets/<KEY>.md` мог вестись лог. Определи ключ из ветки / контекста сессии — **не спрашивай его у пользователя без нужды**.
- **Если ключ определить не удалось** — подставь плейсхолдер `[PROJ-####]`, чтобы пользователь сам вписал номер: `[PROJ-####] короткое описание`.
- **Формат обязателен для любого MR** — docs-only, chore, hotfix, ветка без ключа в имени. Исключений нет.
- **Не переноси в заголовок MR conventional-commit-префикс** (`docs(KEY): …`, `feat(KEY): …`, `fix(KEY): …`). Он для сообщений коммитов; в заголовке MR ключ стоит в квадратных скобках в начале. `docs(PROJ-123): база бенчмарка` — неверно, `[PROJ-123] База бенчмарка` — верно.
- **Короткое описание** — краткая суть того, что появляется в target после мержа. Формулируй по итоговому diff, а не по первому коммиту ветки (первый коммит мог быть про подход, который уже выкинули). Весь заголовок целиком — максимум 72 символа.

Правило действует и когда MR заводится **без этого скилла** — прямым `glab mr create`. Заголовок уже созданного MR правится на месте: `glab mr update <N> --title "[KEY] …"`, пересоздавать не нужно.

### Описание MR

Формат:
```markdown
## Что сделано
- <изменение, которое реально присутствует в итоговом diff>
- <ещё одно>
```

Каждый пункт должен соответствовать чему-то, что ревьюер увидит в diff. Если пункт нельзя показать пальцем в diff — его в описании быть не должно.

**Запрещено в описании:**
- любые упоминания промежуточных версий решения («сначала сделали через A, потом переделали на B»);
- глаголы движения по истории («заменили», «отказались от», «переделали») в применении к коду внутри этой же ветки — только в применении к коду target до мержа;
- количество добавленных/изменённых/удалённых строк;
- перечисление изменённых файлов;
- секция «Изменения» со статистикой.

### Самопроверка перед созданием MR

Прежде чем передавать описание в `glab mr create`, перечитай его и сверь с `git diff --stat`:

1. Каждый пункт описания → есть ли соответствующее изменение в diff? Если нет — удали пункт.
2. Есть ли в описании слова «сначала», «потом», «затем», «изначально», «в итоге», «в конечном счёте», «переделали», «заменили на», «отказались»? Если да — почти наверняка это пересказ процесса. Перепиши пункт как утверждение о конечном состоянии.
3. Можно ли понять описание, не зная, как ветка развивалась коммит за коммитом? Должно быть «да».

## Шаг 5: Создание MR

```bash
glab mr create \
  -t "<заголовок>" \
  -d "<описание>" \
  -b {TARGET_BRANCH} \
  -a {CURRENT_USER} \
  --remove-source-branch \
  {--draft если IS_DRAFT} \
  --yes
```

**Важно:** `--remove-source-branch` добавляется всегда для чистоты после merge. Если пользователь не хочет этого — пусть укажет в Arguments.

## Шаг 6: Результат

После создания MR выведи:

```
✓ MR создан: <URL>
  Ветка: {CURRENT_BRANCH} → {TARGET_BRANCH}
  Assignee: {CURRENT_USER}
  Статус: {Draft / Ready}
```

Если MR для этой ветки уже существует — `glab mr create` вернёт ошибку или ссылку на существующий. В этом случае покажи ссылку на существующий MR и предложи обновить его описание через `glab mr update`.

## Обработка ошибок

- **glab не найден** → сообщи: "Установи glab: `brew install glab`"
- **Не авторизован в GitLab** → сообщи: "Выполни `glab auth login`"
- **Нет remote** → сообщи о необходимости настроить remote
- **Push заблокирован правилами GitLab** → покажи ошибку и остановись

## ➡️ Следующий шаг в рабочем процессе

Место в цепочке: **брейншторм → план → реализация → ревью → ручной тест → MR**.
Этот скилл — **шаг 6 (создание MR)** и **последнее звено** цепочки. Дальше по фича-процессу самостоятельного следующего шага нет.

После того как MR создан и выведена ссылка, предложи пользователю завершить работу над веткой — но **не делай этого сам**: удаление worktree разрушительно и требует явной команды. Покажи подсказку:

```
MR создан. Когда ревьюеры дадут добро и MR будет смержен — можно удалить worktree и локальную ветку.
```
