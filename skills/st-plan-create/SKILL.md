# Создание плана реализации

План пишется вместе с пользователем: он вызвал скилл, чтобы пройти путь диалогом, а не получить готовый
файл. Поэтому внутри скилла авто-режим не действует: каждый AskUserQuestion — остановка до явного ответа,
«разумный дефолт» не выбирается. Исключение — Шаг 0 (worktree): он выполняется без вопроса.

Итог: `docs/plans/yyyymmdd-<task-name>.md` по [template.md](template.md), закоммиченный в worktree,
плюс команда для следующего шага.

## Шаг 0. Worktree

Планирование и реализация не идут в основном чекауте. До разбора задачи:

1. Имя ветки из аргументов: семантический префикс (`feat/`, `fix/`, `refactor/`, `chore/`) и slug из
   задачи, английскими словами без транслита. Объём ещё не обсуждён, slug может быть приблизительным.
   Это пример конвенции именования — замени на принятую в твоей команде.
2. `EnterWorktree` с этим `name` (не `git worktree add` вручную).
3. Сказать пользователю, какая ветка и worktree созданы.

Сессия уже в worktree (`git rev-parse --git-dir` и `git rev-parse --git-common-dir` не совпадают) —
отметить и идти дальше, worktree в worktree не вкладывать.

## Шаг 0.5. Контекст

Определи тип задачи по аргументам (фича, багфикс, рефакторинг, миграция, неясный запрос) и запусти
Explore-агента: связанный код и паттерны, затронутые компоненты и зависимости, для бага — логи и
недавние изменения, для рефакторинга — покрытие тестами, для неясного запроса — `git status` и структура
проекта. Сведи в сводку: что в работе, какие файлы, какая цель, какие паттерны.

## Шаг 0.7. Спека

Есть `docs/plans/*-spec.md` для этой работы (обычно от `st-spec-create` прямо перед этим) — прочитай
целиком, это решённая постановка:

| Спека фиксирует | План |
|---|---|
| Problem Statement, Solution | не переоткрывает цель |
| User Stories | превращает каждую в задачи, все покрыты |
| Implementation Decisions | следует им, дизайн не переоткрывает |
| Testing Decisions | по одному чекбоксу-тесту на каждую строку списка поведений, ни одного сверх; швы — согласованные |
| Out of Scope | не трогает |

Спрашивай только о пробелах: вопросы Шага 1, на которые спека отвечает, пропусти и одной строкой скажи
какие. Не согласен со спекой — скажи один раз, решает пользователь; молча планировать другое нельзя,
иначе Spec Coverage в ревью расходится с реальностью. Спеки нет — Шаг 1 целиком.

## Шаг 1. Вопросы по одному

Покажи сводку контекста, затем AskUserQuestion по одному вопросу, с вариантами из разведки:

1. цель — «что главное должно получиться?»;
2. объём — «какие компоненты и файлы затронуты?»;
3. ограничения — «требования, лимиты, совместимость?» (можно открытым текстом).

Имя файла плана не спрашивается: выведи из задачи и ключа тикета (`<ticket>-<slug>` или `<slug>`,
английский slug). Есть спека — имя берётся из неё: `20260904-md-link-patcher-spec.md` →
`20260904-md-link-patcher.md`, символ в символ, иначе план не свяжется со спекой. Несколько спек без
очевидного соответствия — единственный допустимый вопрос про имя.

## Шаг 1.5. Подходы

Предложи 2–3 подхода с плюсами и минусами, рекомендуемый первым и с обоснованием, разговорно, не
документом. Выбор — через AskUserQuestion. Пропусти шаг, если путь один, пользователь уже сказал как,
или это багфикс с очевидным решением.

## Шаг 2. Файл плана

**План — решения, не реализация.** Его исполняет агент без доступа к этому диалогу: план говорит, что
построить и почему, с ограничениями, контрактами и отклонёнными альтернативами; код исполнитель напишет
сам, читая кодовую базу. Фразы «как обсуждали», «см. выше» недопустимы.

В план входит: требования и ограничения из Q&A; выбранный подход с причиной и отклонённые альтернативы;
контракты API на границах системы (форма запроса и ответа на уровне провода); схемы хранимых данных;
краевые случаи, которые обсуждались; неочевидные ограничения (производительность, совместимость,
безопасность).

В план не входит: сигнатуры функций, имена классов и хелперов; код и псевдокод; пошаговый пересказ потока
(«распарсить, провалидировать, вызвать, вернуть»); примеры вызовов библиотек; паттерны, которые видны в
существующих файлах (дай ссылку на модуль-образец); пересказ репозитория — что функция уже делает, из
каких файлов состоит модуль, какие у проекта дефолты (исполнитель читает код сам). Поймал себя на `def foo(`, `class Foo` или списке
«вызвать X, потом Y» — удали: две копии реализации расходятся, а исполнитель выберет идиоматичный код
лучше, чем написанный вслепую при планировании.

Проверь `docs/plans/` на существующие файлы, создай `docs/plans/yyyymmdd-<task-name>.md` по
[template.md](template.md).

**Формат задачи** — `st-plan-exec` отслеживает прогресс, переключая `[ ]` в `[x]`, поэтому:

1. заголовок `### Task N: <конкретное имя>`, не «Core Logic»;
2. блок `**Files:**` с `Create:` / `Modify:` и точными путями — всегда, даже для одного файла;
3. каждое действие в теле — чекбокс `- [ ]`; прозы, простых буллетов и нумерованных списков в теле нет;
4. тесты — отдельными чекбоксами, по одному на поведение, с именем поведения из Testing Decisions
   спеки (без спеки — из критериев приёмки): «тест: отклоняет заявку сверх лимита». Чекбокс «тесты на
   ошибки и краевые случаи» без названного поведения — это не чекбокс, а приглашение исполнителю
   выдумать тесты;
5. последний чекбокс — прогон тестов, зелёные до следующей задачи.

Одна задача — одна логическая единица (функция, эндпоинт, компонент), около пяти чекбоксов.

**Самопроверка перед сохранением**, по каждой задаче:

- уровень абстракции: пункт читается как комментарий внутри кода («распарсить JSON в UserRequest»,
  «bcrypt cost 12») → переписать как результат («принять вход по контракту из Technical Details»);
  в Technical Details поле структуры, не пересекающей границу процесса, → удалить;
- документация: задача про доки требует описать состояние **после** деплоя в настоящем времени, шаги
  раската и миграции — в Post-Completion; формулировки «нужно будет», «после деплоя включи», «will»
  дадут переходную доку, которая протухнет в момент мержа;
- дубль: факт уже записан в другой секции — критерий приёмки повторён чекбоксом, решение повторено в
  Technical Details, список файлов из Context повторён блоками Files → оставить в одном доме, во
  втором ссылка или ничего;
- выводимость: утверждение грепается в репозитории за один вызов (текущая сигнатура, что функция уже
  делает, состав модуля, дефолт проекта, правило из CLAUDE.md) → удалить; в Context остаётся только
  то, чего в репозитории нет;
- тесты: каждый чекбокс-тест называет поведение; поведение, которого нет ни в Testing Decisions,
  ни в критериях приёмки, → удалить;
- формат: блок Files есть, все действия — чекбоксы, последний — прогон тестов.

## Шаг 3. Авторевью

Сообщи: «Создан план `<путь>`. Запускаю ревью…» и запусти два ревью параллельно в одном сообщении:

1. Agent с `subagent_type=plan-review`, в промпте — путь к плану и, если есть, путь к спеке (блок Spec
   Coverage сверяет план с ней). Чеклист у агента свой, не пересказывай. Не `Plan`: тот ревьюит по
   тому, что вывел из промпта, а `plan-review` — по фиксированному чеклисту, результаты сравнимы.
2. Codex через Bash (`timeout: 600000`): промпт в `/tmp/plan-codex-review.md` — «Review the
   implementation plan at <plan-file-path>. Check for: completeness, feasibility, missing edge cases,
   incorrect assumptions, gaps in implementation approach, and whether tasks are properly ordered. Also
   flag over-specification: checklist items that prescribe implementation the executor should choose,
   facts repeated across sections, and context the executor can read from the code. Flag test
   checkboxes that name no behavior or cover a case the spec does not require. Propose concrete
   cuts. Be critical and specific.» — и

   ```bash
   codex exec --sandbox read-only --ephemeral --color never -C <repo> \
     -o /tmp/plan-codex-review.out.md - < /tmp/plan-codex-review.md
   ```

   Ответ — в `/tmp/plan-codex-review.out.md`; ненулевой код выхода или пустой файл (сбой, исчерпанная
   квота) — ревью только от plan-review с пометкой в сводке.

Дождись обоих. Сырые отчёты пользователю не показывай — сначала триаж.

**Триаж.** По каждому замечанию две оси. *Валидность*: перечитай нужное место плана, не верь уверенному
тону; «отсутствует X» — проверь, нет ли X под другим заголовком; техническая претензия — проверь, что
она относится к выбранному подходу, ревьюеры не знают ограничений из Q&A. *Применимость*: замечание к
плану как документу (пропущенная задача, неясный критерий приёмки, неверный путь, сломанный формат,
пробел контракта на границе) → применить; замечание про детали реализации (имена, внутренние типы,
обработка ошибок на уровне кода) → отклонить с причиной «деталь реализации, решает исполнитель»;
расширение объёма → на решение пользователя; дубли двух ревьюеров → одно решение; противоречие →
выбрать согласное с требованиями пользователя, неоднозначно → пользователю; замечание про **лишнее** —
пункт предписывает реализацию, факт повторён в двух секциях, контекст выводится из кода, чекбокс-тест
на поведение вне спеки и критериев приёмки → сократить по
умолчанию, исключение: факт пришёл из Q&A с пользователем, тогда перенести в единственный дом, а не
удалять.

Ревьюеры по своей природе тянут план вверх по объёму: каждое их замечание можно закрыть дописыванием.
Исход «сократить» — единственное, что уравновешивает эту асимметрию, поэтому применяй его так же
охотно, как «применить».

Принятое внеси в план Edit-ом, сохранив формат из Шага 2, с вытекающими правками (перенумерация задач,
новый контракт в Technical Details); по тронутым задачам повтори самопроверку. Затем сводка:

```
Авторевью завершено. Найдено N замечаний.

Применено в план (M):
- <суть> — <где: Task X / Overview / Technical Details>

Сокращено (S):
- <что убрано или перенесено> — <откуда: Task X / Context / Overview> — <куда, если перенесено>

Отклонено (K):
- <суть> — <причина>

Требует твоего решения (L):   ← только при расширении объёма или неоднозначности
- <суть> — <почему не решил сам>
```

Пункты «Требует решения» — AskUserQuestion по одному, ответы внести в план. Всё применено или отклонено —
сразу к аннотации, без подтверждения триажа: пользователь ещё может править план на следующем шаге.

## Шаг 4. Аннотация и коммит

Спроси, как аннотировать:

```json
{"questions": [{"question": "Как хочешь проаннотировать план?", "header": "Annotator", "multiSelect": false,
  "options": [
    {"label": "st-plan-annotate", "description": "Открыть план в $EDITOR (tmux/kitty/wezterm split), поддерживает #ASK-комментарии"},
    {"label": "plannotator-annotate", "description": "UI плагина plannotator для визуальной аннотации"},
    {"label": "Пропустить", "description": "Без ручной аннотации — сразу коммит"}]}]}
```

- **st-plan-annotate** — Skill с путём к плану; по завершении цикла — к коммиту.
- **plannotator-annotate** — `/plannotator-annotate` с путём к плану; вернувшиеся аннотации отработать,
  нет аннотаций — нечего.
- **Пропустить** — к коммиту.

После аннотации (или пропуска) закоммить план в worktree без вопроса: `docs: add <topic> implementation
plan`. Task 1 не начинать. Закончи командой для следующего шага в свежей сессии — реализация тяжёлая,
чистый контекст надёжнее:

```
Следующий шаг — реализация плана. В новой сессии (/clear или новое окно):

/st-plan-exec <path_to_plan>
```

Место в цепочке: брейншторм → план → **реализация** → ревью → ручной тест → MR.

## Принципы

- Один вопрос за раз, варианты ответа предпочтительнее открытого текста.
- Рекомендация первой, с причиной; решает пользователь.
- DRY и YAGNI: объём минимальный; повтор кода предпочтительнее преждевременной абстракции, если снижает
  связность — при повторе спроси пользователя, что предпочесть.
- План самодостаточен: всё решённое в диалоге записано в файл.
