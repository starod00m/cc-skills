# Шаблон плана `docs/plans/yyyymmdd-<task-name>.md`

Заголовки секций свободны — их никто не парсит. Обязательны четыре вещи, потому что на них завязаны
скиллы и ссылки внутри плана: заголовок задачи `### Task N:`, блок `**Files:**`, чекбоксы `- [ ]` и
имя секции `## Technical Details`, на которое ссылаются чекбоксы. Текст в угловых скобках заменяется
содержимым; пояснения курсивом в план не переносятся.

Ориентиры объёма: Overview ≈ 40 строк, Context ≈ 15, план целиком 250–300. Это повод спросить «что
здесь лишнее», а не обязанность резать. Решил сокращать — выноси факт в его единственный дом
(тикет-лог, спека, `Technical Details`), а не ужимай формулировки: иначе плотность растёт от правки
к правке и уже не падает.

```markdown
# <Название плана>

## Overview
- что делаем и зачем: <2–3 строки; предыстория — ссылкой на тикет-лог, спеку или design-brief, не пересказом>
- критерии приёмки: <что значит «готово», конкретно; команда полного прогона тестов; e2e — команда или «нет»>
- выбранный подход и почему: <один абзац>
- решения, которых исполнитель не выведет из кода: <по 1–2 строки, каждое с причиной; сюда же
  неочевидные ограничения тестов>
- отвергнутые альтернативы: <по строке каждая, с причиной — чтобы исполнитель не переоткрывал>
- порядок задач: <1–2 строки, только если он не очевиден>

## Context (from discovery)
*Только то, чего нет в репозитории: факты с прода, идентификаторы дашбордов и внешних систем, грабли,
найденные в разведке. Список затронутых файлов не сюда — он в блоках `Files` задач.*

- <находка, которую исполнитель не получит, прочитав код>

## Implementation Steps

### Task 1: <конкретное имя — что делает задача>

**Files:**
- Create: `точный/путь/к/новому`
- Modify: `точный/путь/к/существующему`

- [ ] <один проверяемый результат в строку; вместо повтора — «по контракту из Technical Details»
      или «по решению из Overview»>
- [ ] <действие>
- [ ] тест: <поведение из Testing Decisions спеки или критериев приёмки — по чекбоксу на поведение>
- [ ] прогнать тесты — зелёные до следующей задачи

### Task N-1: Verify acceptance criteria
- [ ] все требования из Overview реализованы
- [ ] полный прогон тестов: `<команда проекта>`
- [ ] e2e, если есть: `<команда>`

### Task N: [Final] Update documentation
- [ ] README / docs — состояние ПОСЛЕ деплоя в настоящем времени, без шагов раската и миграций
- [ ] CLAUDE.md, если появились новые конвенции

## Technical Details
*Только контракты на границах системы — где ошибка в форме сломает интеграцию с тем, чего исполнитель
не видит. Внутренние типы и сигнатуры не сюда.*

- внешние API: <путь, метод, поля запроса и ответа, коды>
- хранимые данные: <таблицы, колонки, форма миграции, форматы файлов>
- межсервисные сообщения: <payload очереди, форма события>
- ограничения, не выводимые из кода: <производительность, совместимость, безопасность — из Q&A>

## Post-Completion
*Без чекбоксов: действия вне репозитория.*

- ручная проверка: <сценарии>
- внешние системы: <потребители библиотеки, конфиги деплоя, порядок раската, флаги, миграции>
```

## Чего в плане нет

- **Как исполнять план.** «Задачи по одной», «тесты зелёные до следующей», «обнови план при смене
  объёма», конвенции `[x]` / ➕ / ⚠️ — это дом `st-plan-exec`, а не плана. План описывает, что
  построить, а не как оркестратор ведёт прогон.
- **Перенос плана в `docs/plans/completed/`** отдельным чекбоксом: архивацию делает `st-plan-exec`
  после всех фаз. Чекбокс, который просит подвинуть файл в середине прогона, ломает ревью и
  статистику, которые этот файл читают.
- **Отдельная секция Testing Strategy.** Команда прогона и наличие e2e — в критериях приёмки,
  неочевидные ограничения тестов — в решениях Overview, остальное задаётся чекбоксами задач.
- **Пересказ репозитория.** Текущие сигнатуры, состав модулей, что функция уже делает, дефолты
  проекта — исполнитель читает код сам.
