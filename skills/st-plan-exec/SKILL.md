# Исполнение плана

Пользователь запустил автономный прогон и ушёл. Значит вопросов внутри нет: развилки внутри
согласованного объёма решают исполнители сами и записывают решение в журнал, а ты в конце
показываешь пользователю всё, что решили за него. Останавливает прогон только настоящий блокер.

**Ты — оркестратор.** Код не читаешь, тесты не запускаешь, ошибки не чинишь, план не правишь.
Всё это делают сабагенты. Твой контекст — номера тасков, отметки успеха и строки журнала; как
только в него попадают логи тестов и куски файлов, последние таски исполняются хуже первых.

Прогон: worktree → журнал → таски → ревью → статистика → архивация → отчёт. Он не заканчивается на
ревью: статистика, архивация и финальный отчёт обязательны и при вызове из другого скилла —
управление возвращается вызывающему только после Шага 6. Без Шага 6 пользователь не узнаёт, что
прогон решил за него.

## Контекст от пользователя

$ARGUMENTS

Путь к плану берётся отсюда. Есть в аргументах «без ревью», «только таски», «--no-review» —
Шаг 3 пропускается, это фиксируется в журнале и в финальном отчёте.

## Scope: чего скилл не делает

Скилл исполняет план **локально**. Всё, что видно другим людям или необратимо, — вне его границ
и требует отдельного запроса пользователя:

- `git push` в любой форме, включая `-u origin`, `--force`, `--force-with-lease`;
- создание PR/MR любым способом (`gh pr create`, `glab mr create`, web-UI, API);
- `git merge` фича-ветки в base-ветку;
- `git branch -d/-D`, `git worktree remove`, `git push --delete`;
- перезапись истории: `--amend`, `rebase`, `reset --hard`;
- любые сетевые операции, меняющие remote (`fetch`/`pull` для чтения — можно, если нужно плану).

**Автономный режим этот запрет не отменяет.** Он разрешает решать развилки внутри согласованного
объёма, а не расширять границы скилла. Публикация работы — решение пользователя, принимается после
того, как он посмотрит результат.

Исключение: план прямо предписывает запушить или создать MR — это явный апрув для работы по этому
плану.

## Шаг 0. Worktree

Работа идёт в изолированном worktree. Определи, где ты:

```bash
git rev-parse --git-dir
git rev-parse --git-common-dir
```

Значения **не совпадают** — ты уже в linked worktree (обычный случай: план создавался в нём же
через `st-plan-create`). Скажи одной строкой «Уже в worktree `<cwd>`, ветка `<ветка>`» и иди
дальше, вопросов не задавай: окружение настроено заранее.

Значения **совпадают** — ты в обычном чекауте. Спроси через AskUserQuestion, создавать ли worktree
(рекомендуется). Согласие — прочитай заголовок плана, собери имя ветки (`feat/`, `fix/`,
`refactor/`, `docs/`, `chore/`, `test/` плюс kebab-slug из плана английскими словами, до 40
символов, без транслита и без слова `worktree`; это пример конвенции — замени на свою) и вызови
`EnterWorktree` с этим `name`. Отказ —
работай в текущей ветке и предупреди об этом.

На `main`/`master` реализацию не начинай без явного согласия пользователя.

## Шаг 0.5. Журнал прогона

Журнал переживает `/clear` и смену сессии, и его читает `st-review` следующим шагом.

`.plan-exec/<имя плана без расширения>.md` → `$LOG`. Проверь, что `.plan-exec/` есть в
`.gitignore`; нет — добавь строкой и скажи об этом. Файл уже существует (перезапуск прогона) —
прочитай, продолжай дописывать в те же секции, не затирай.

```markdown
# Plan Exec: <ветка>

- **Дата:** YYYY-MM-DD
- **План:** <путь>
- **Ветка / worktree:** <ветка> — <путь или «без worktree»>
- **Ревью:** st-review | пропущено (по запросу пользователя)

## Задачи

## Решения и отклонения
```

Дописывай в `$LOG` через Edit по ходу прогона, а не пачкой в конце: упавший прогон должен оставить
после себя всё, что успел.

## Шаг 1. Загрузка плана

Прочитай план, посчитай секции `### Task N:` — это объём. Заведи задачи через TaskCreate: по одной
на каждую секцию плюс `Ревью (st-review)`, `Статистика`, `Архивация`. Отмечай их по ходу.

Просмотри план критически. Дальше две разные ситуации:

- **Блокер** — план прямо противоречит коду, в нём критический пробел, без которого нельзя начать,
  или он требует необратимого действия без авторизации. Остановись и спроси пользователя.
- **Несогласие** — сделал бы иначе, но план исполним. Строка в `$LOG` (`[deviation] plan: …`) и
  работай по плану. Автономный прогон не место переоткрывать согласованные решения.

## Шаг 2. Цикл тасков

Повторяй, пока в секциях `### Task N:` остаются `[ ]`:

1. **Перечитай файл плана.** Сабагент правит его каждую итерацию.
2. Найди **первую** секцию с незакрытыми `[ ]`. Нет такой — все таски готовы, к Шагу 3.
3. **Объяви таск пользователю**: номер, заголовок, список `[ ]` этой секции.
4. **Запусти один сабагент** — Agent tool, `subagent_type: "general-purpose"`, промпт из
   [references/task-prompt.md](references/task-prompt.md) с подставленными путями плана и `$LOG`.
5. **Перечитай план и проверь чекбоксы этой секции.** Отмечены — таск засчитан. Не отмечены —
   ретрай свежим сабагентом (лимит: 1 на таск), передав в промпт, что именно осталось и что
   сообщил предыдущий. Ретрай исчерпан — остановись и отчитайся пользователю.
6. **Запиши в `$LOG`** строку `[task] Task N: <заголовок> — готово (<hash коммита>)` либо
   `— ПРОВАЛ, ретрай 1`. Строки `[test]` / `[decision]` / `[deviation]` из отчёта сабагента перенеси
   в секцию «Решения и отклонения» как есть.
7. **Пользователю — одна строка**: «Task N завершён». Подробности живут в журнале.

Правила цикла, каждое из которых уже ломалось:

- **Ровно один сабагент за итерацию, дождаться возврата.** Таски упорядочены и правят один и тот
  же файл плана и пересекающиеся файлы кода; параллельный запуск портит и план, и дерево.
- **Условие выхода — только состояние чекбоксов в файле**, а не текст отчёта сабагента. «Сделал
  всё» при неотмеченных чекбоксах — это провал таска, а не успех.
- **Чекбоксы за сабагента не отмечай.** План правит исполнитель; оркестратор, дописывающий `[x]`,
  скрывает ровно ту поломку, которую эта проверка и должна ловить.
- **Сабагент оставил сломанный код** (ошибки компиляции, красные тесты, линтер) — не чини сам,
  перезапусти таск, передав детали в промпт.
- Предохранитель: 50 итераций. Достиг — стоп и отчёт.

## Шаг 3. Ревью

Пропущено, если пользователь сказал «без ревью» — тогда строка в `$LOG` и сразу Шаг 4.

Иначе — полный цикл `st-review`, обе фазы (Claude, затем Codex), в **сабагенте-Ревьюере**, а не в
этой сессии: ревью — самая тяжёлая часть прогона (по замерам 300–430k контекста), и в твоём контексте
оно вытесняет всё остальное. Сабагент сам порождает ревьюеров, валидатора и фиксера (вложенные
сабагенты) и возвращает тебе только итог.

Agent tool, `subagent_type: "general-purpose"`, промпт:

```
Вызови скилл `st-review` через Skill tool с аргументами: `<путь к плану> <$LOG> автономный режим` —
и выполни его до конца. Вопросов не задавай. Финальным сообщением верни дословно ответ скилла по его
контракту (DONE | BLOCKED | FAILED, не больше 15 строк) — ничего сверх.
```

По пометке `автономный режим` `st-review` не задаёт вопросов, передаёт журнал ревьюерам (чтобы они не
переоткрывали то, что исполнитель уже решил осознанно) и не чинит расхождения со спекой, а пишет их в
`$LOG` как `[escalation]`. Ведёт собственный лог `.review/` и коммитит исправления сам.

Дождись возврата Ревьюера; `ListAgents` не опрашивай — уведомление о завершении придёт само. Дальше:

- `DONE` — строка `[review] <итог одной строкой>` в `$LOG`, к Шагу 4;
- `BLOCKED` / `FAILED` — остановись и отчитайся пользователю, как о блокере прогона: план не
  архивируй.

## Шаг 4. Статистика

Один сабагент, `subagent_type: "general-purpose"`, промпт из
[references/stats-prompt.md](references/stats-prompt.md) с подставленной базовой веткой. Он читает
JSONL-логи этой сессии, агрегирует токены, время и число агентов по фазам, добавляет `git diff
--shortstat` и возвращает компактный markdown.

Вывод покажи пользователю дословно и допиши в `$LOG` — он уже сжат, второй раз сжимать нечего.

Шаг best-effort: агент упал или логи не нашлись — строка «Статистика недоступна: <причина>» и
дальше. Прогон это не блокирует.

## Шаг 5. Архивация плана

Внутри worktree:

1. `mkdir -p docs/plans/completed`;
2. `git mv docs/plans/<план>.md docs/plans/completed/`;
3. **парная спека** `docs/plans/<план без .md>-spec.md`, если есть, — тем же движением: спека,
   оставшаяся в `docs/plans/`, читается как незакрытая работа. Нет файла — молча пропусти,
   у большинства планов спеки нет;
4. коммит: `chore: архивировать выполненный план <план>`.

## Шаг 6. Финальный отчёт

Допиши в `$LOG` и покажи пользователю:

```markdown
## Итог

- **Ветка / worktree:** <ветка> — <путь>
- **Тасков:** N выполнено из M
- **Ревью:** <итог Ревьюера одной строкой, путь к `.review/` логу> | пропущено
- **Коммиты:** <git log --oneline $BASE..HEAD>
- **Статистика:** <вывод Шага 4>

### Решено автономно / отклонения от плана
- [decision] task 3: … — <почему>
- [deviation] task 5: … — <почему>

### Требует твоего решения
- [escalation] review: … — <что именно не решено>
```

Секцию «Решено автономно» собери из `$LOG` по маркерам `[decision]` и `[deviation]`, секцию
«Требует твоего решения» — по `[escalation]`. Пусто — так и напиши одной строкой; это не
формальность, а единственное место, где пользователь узнаёт, на какие вопросы прогон ответил без
него.

Пункты «Требует твоего решения» после прогона больше нигде не живут. Предложи одной строкой завести
их в бэклог — там они переживут ветку и всплывут, когда до них дойдут руки.

Тесты сам не запускай: их статус уже зафиксирован сабагентами в журнале.

Закончи путём к журналу и командой следующего шага:

```
Полный журнал прогона: .plan-exec/<план>.md

Следующий шаг — ручной тест. В новой сессии (/clear или новое окно):

/st-manual-test <что сделано / путь к заархивированному плану>
```

Место в цепочке: брейншторм → план → **реализация с ревью** → ручной тест → MR. Push, MR, merge и
удаление веток — отдельные решения пользователя, см. «Scope».
