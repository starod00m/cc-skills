# Итеративный цикл ревью

Координируй ревью: сам код не читай и не правь, находки ревьюеров тоже не читай. Ревьюеры пишут их в
файлы, валидатор и фиксер работают по путям, тебе возвращаются строки-счётчики. Твой контекст — номера
итераций, счётчики и короткие итоги; как только в него попадают отчёты ревьюеров и diff, поздние
итерации координируются хуже ранних, а при запуске из `st-plan-exec` раздувается и его сессия.

Два прохода по одной схеме: **Фаза 1** — Claude-агенты, **Фаза 2** — Codex по уже исправленному коду
(ищет то, что Claude пропустил). Внутри каждого прохода итерация — это цепочка

```
ревью (все роли параллельно, дождаться всех) → валидация → исправление с коммитом → решение
```

Три правила держат цикл, остальное — детали:

1. Следующий прогон ревью начинается только после коммита текущей итерации; замечания между итерациями
   не копятся. Иначе следующие ревьюеры увидят грязное дерево, а правки нельзя будет откатить по одной.
2. Фаза 2 стартует только после того, как Фаза 1 завершилась (итерация с нулём принятых или лимит).
   Codex дорогой и независимый: его смысл — свежий взгляд на стабильный код, а не чередование с Claude.
3. Вопросов пользователю нет ни на старте, ни по ходу цикла: план, база и параметры определяются
   автоматически, способ исправления замечания выбирают валидатор и фиксер. Спорное решение не блокирует
   итерацию — выбор и причина идут в `$LOG` и в финальный отчёт. Codex включён по умолчанию,
   отключается только явным «без codex» / «только claude» в аргументах или беседе.

Лимит — 5 итераций на фазу. Фаза 1 упёрлась в лимит с принятыми замечаниями — всё равно переходи к
Фазе 2 и отметь в `$LOG` «Фаза 1 не сошлась за 5 итераций».

В промпты и сообщения агентам подставляй **значения** (`$BASE` → хэш, `$RUN` → путь), а не имена
переменных: у агента их нет.

**Автономный режим.** В `$ARGUMENTS` есть `автономный режим` — так скилл вызывает `st-plan-exec`
(из сабагента-Ревьюера), и человека рядом нет: AskUserQuestion не вызывается ни на одном шаге.
Замечание, которое требует решения пользователя, не фиксится — оно уходит строкой `[escalation]` в
журнал прогона и в финальный отчёт. Финальный ответ — по контракту из раздела «Финальный отчёт».

## Контекст от пользователя

$ARGUMENTS

## Шаг 0. База, план, лог, бриф

Сначала `.review/` в `.gitignore`: нет — допиши строкой и скажи об этом. Затем `git status`:

- грязный только `.gitignore` (строки служебных каталогов — `.review/`, `.plan-exec/`, их дописывают
  этот скилл и `st-plan-exec`) — закоммить его отдельно: `chore: игнорировать служебные каталоги`;
- грязное что-то ещё — не чисти дерево сам: в автономном режиме финальный ответ `BLOCKED` («грязное
  дерево на старте ревью»), при ручном запуске скажи пользователю и остановись.

**База.** Основная ветка — `main`, `master` или `develop`; `git merge-base HEAD <основная>` → `$BASE`.
Если текущая ветка и есть основная — `$BASE = HEAD~1`. Полный diff и тела коммитов не собирай:
ревьюеры берут их сами.

**План** — путь, не содержимое. Первый найденный источник:

1. Путь к файлу в `$ARGUMENTS` (есть `/` и расширение `.md`/`.txt`/`.rst`, либо `docs/`, `plans/`,
   `specs/`, `tz/`), кроме путей под `.plan-exec/` — это журнал прогона → `$PLAN`.
2. Файл, добавленный или изменённый в фичебранче (`git diff --name-only --diff-filter=AM $BASE...HEAD`)
   под `docs/plans/`, `plans/`, `tz/`, `specs/` либо `plan*.md`, `spec*.md`, корневой `README*.md`.
   `*-spec.md` — не план, а спека. Несколько кандидатов — приоритет `docs/plans/` → `plans/` → `tz/` →
   `specs/`, не больше трёх путей в `$PLAN`.
3. Иначе `$PLAN` пуст: ревьюеры ориентируются на `$ARGUMENTS`, commit narrative и код.

**Спека** — парный файл `<план без .md>-spec.md`; нет плана или пары — единственный
`docs/plans/**/*-spec.md` в фичебранче. Несколько без очевидного соответствия — `$SPEC` пустая, не угадывай.
`$SPEC` получает только `spec-reviewer`: остальные меряют «как сделано», ему лишний контекст.

**Журнал прогона** — путь к `.plan-exec/*.md` в `$ARGUMENTS` → `$EXEC_LOG`. Его секция «Решения и
отклонения» идёт ревьюерам как история (по пути, через бриф): исполнитель уже взвесил эти развилки и
записал почему, переоткрывать их — шум. Строки `[escalation]` в этот же файл дописывает валидатор. Пути
нет — `$EXEC_LOG` пуста.

Сообщи по одной строке: откуда взят план, найдена ли спека, подхвачен ли журнал прогона.

**Лог** — один на ветку: Glob `.review/*-<ветка>.md` (`/` в имени ветки → `-`), самый свежий → `$LOG`.
Нет — `.review/YYYY-MM-DD-<ветка>.md`. Рабочие файлы запуска — в `$RUN` = `.review/<имя лога без .md>/`. `$LOG` — ещё и история для
ревьюеров: принятые и отклонённые с причинами они читают из него сами.

Состояние лога определяй через Grep с номерами строк, не читая его целиком: `^### Повторный запуск`,
`^## Итог`, `^## Итерация`, `^### Фаза 1 \(Claude\) завершена`. Смотри только часть после последнего
`### Повторный запуск` (или весь лог, если его нет):

- Лога нет — создай шапку (ниже). Обычный запуск.
- В этой части нет `## Итог` — прерванный прогон: продолжай ту же фазу с номера последней итерации + 1
  и с остатком лимита фазы. Фаза 1 уже завершена — `$PHASE2_BASE` возьми из её строки. Какие роли
  дали принятые на прошлой итерации, память валидатора не сохранила — первую итерацию после
  возобновления гоняй набором фазы без ролей «только итерация 1».
- В этой части есть `## Итог` — **повторный запуск** после новых правок (например, self-fix после
  ручного теста). `$RERUN_BASE` = хэш из строки `- **HEAD:**` последнего итога (лог старого формата без
  этой строки — `$BASE`). Допиши
  `### Повторный запуск: <дата>, база $RERUN_BASE`. Нумерация итераций продолжается, счётчики фаз — с
  нуля, область и состав — по таблице итераций (строка «повторный запуск»).

```markdown
# Review Log: <ветка>

- **Дата:** YYYY-MM-DD
- **База:** $BASE → HEAD
- **Контекст:** $ARGUMENTS
- **План:** <путь | «не найден — использован контекст»>
- **Спека:** <путь | «не найдена»>
- **Журнал прогона:** <путь | «нет»>
- **Codex:** да | нет
```

Секции итераций в `$LOG` пишут валидатор и фиксер; ты дописываешь только строки фаз, повторных
запусков и сбоев.

**Бриф** — `$RUN/brief.md`, пишется один раз на запуск (Write). Всё, что одинаково для всех ролей и
итераций, живёт здесь, а не в промптах: иначе каждая итерация заново генерирует одни и те же блоки
шести промптов.

```markdown
# Бриф ревью

## Задача
Проведи ревью изменений фичебранча согласно своей специализации.

## Контекст изменений
<$ARGUMENTS>

## План / ТЗ
<пути $PLAN — прочитай их | «План не найден. Ориентируйся на commit narrative и код.»>

## База для diff
$BASE = <хэш>

## Как собрать контекст
- Состав: `git diff --name-only <$BASE>...HEAD`, `git log --oneline <$BASE>..HEAD`.
- Narrative: `git log --format='%n=== %h %s ===%n%n%b' <$BASE>..HEAD`. Diff показывает, что изменилось,
  narrative — почему. Не повторяй замечания, которые автор уже обосновал в commit body (сознательно
  отвергнутая абстракция не повод предлагать её снова).
- Diff бери сам в области, которую задаёт твой промпт. Читай файлы целиком, чтобы видеть контекст.

## История ревью
`<$LOG>` — принятые и исправленные замечания прошлых итераций и отклонённые с причинами. Не поднимай
отклонённое без новой причины, которой в обосновании нет. Ищи новое, включая проблемы от исправлений.

## Осознанные решения исполнителя
<есть $EXEC_LOG: «Прочитай секцию «Решения и отклонения» в <путь>: строки [decision] и [deviation] —
развилки, которые автор взвесил и обосновал; не предлагай отменить их без новой причины. Строки [test] —
правка прода, которую по заявлению автора ловит каждый тест; testing-reviewer сверяет заявление с телом
теста». Нет — секцию не пиши.>

## Формат ответа
Каждое замечание: приоритет (P1 — баги, потеря данных, безопасность; P2 — логика, несоответствие ТЗ,
обработка ошибок; P3 — стиль, именование, упрощение, документация), `файл:строка`, проблема,
процитированное доказательство, как исправить. Промпт ограничил приоритеты до P1/P2 — P3 не расписывай,
а перечисли по строке в конце блоком «P3 — в бэклог».

Запиши замечания нумерованным списком в файл, путь к которому дан в промпте (Write), — это единственный
файл, который ты пишешь; код и остальные файлы не трогай. Финальным сообщением верни одну строку:
`N замечаний (P1: a, P2: b, P3: c)`, а если замечаний нет — ровно `Замечаний нет`, какой бы формулировкой
«пустого» ответа ни пользовались твои инструкции. Промпт говорит «файлы не пиши» — тогда весь список
замечаний и есть финальное сообщение. Агентов не запускай — всё ревью делай сам.
```

Для `spec-reviewer` — отдельный `$RUN/brief-spec.md`: тот же бриф, но вместо `## План / ТЗ` секция
`## Спека` с **текстом** спеки (Read `$SPEC` один раз на запуск и перенеси в бриф). Три условия, без
которых ось схлопывается:

1. Спека — текстом в брифе, не путём: рядом лежит план с почти тем же именем.
2. Строка «План реализации лежит рядом в docs/plans/, не читай его: твой вопрос — то ли построили, а не
   как». Абзац про narrative убери — мотивация автора не отменяет требование спеки.
3. Его замечания валидатор держит отдельным блоком `## Соответствие спеке` с отдельной нумерацией.

## Шаг 1. Состав ревьюеров

| Роль | Когда |
|---|---|
| `quality-reviewer` | в каждом прогоне: баги, безопасность, достигнута ли цель плана |
| `testing-reviewer` | есть тесты в изменениях (добавлены, изменены, удалены, пропущены) или новый код должен быть покрыт |
| `documentation-reviewer` | пользовательские изменения (API, CLI-флаги, конфигурация) или проза в диффе: доки, комментарии, докстринги |
| `spec-reviewer` | найдена `$SPEC` |
| `architecture-reviewer` | только итерация 1 Фазы 1 |
| `simplification-reviewer` | только итерация 1 Фазы 1: много нового кода, новые абстракции, рефакторинг |

Состав итерации 1 (фазы или повторного запуска) выбирай по `git diff --stat` её области. Мелкий
багфикс (1–2 файла, до 20 строк) — только `quality-reviewer`.

**architecture-reviewer** ловит системное, невидимое построчному анализу: фича не работает в одном из
режимов запуска или развёртывания, нарушен runtime-инвариант, параметры одной фичи разбросаны по разным
источникам без причины, парные изменения в смежном репозитории. Запускается вместе со всеми; его
замечания попадают в общий пул итерации 1 и не блокируют детальных ролей.

**documentation-reviewer** ведёт две оси: ось A — чего в документации не хватает, ось B — нарушает ли
написанная в диффе проза правила автора.

**Итерации** — одинаково для обеих фаз:

| | Итерация 1 | Итерации 2+ |
|---|---|---|
| Роли | весь набор (Фаза 2 — набор Фазы 1 без ролей «только итерация 1 Фазы 1») | `quality-reviewer` + роли, от которых на прошлой итерации приняли замечания, кроме ролей «только итерация 1» |
| Приоритеты | все; принятые P3 правятся на этой же итерации | только P1/P2; P3 — в «Кандидаты в бэклог», не фиксятся |
| Область, Фаза 1 | вся ветка `$BASE...HEAD` | вся ветка `$BASE...HEAD` |
| Область, Фаза 2 | вся ветка `$BASE...HEAD` | накопленные фиксы фазы: `$PHASE2_BASE..HEAD` |
| Повторный запуск | область `$RERUN_BASE..HEAD` в обеих фазах и на всех итерациях; состав по размеру этой области, без ролей «только итерация 1» | так же |

`$PHASE2_BASE` — HEAD на старте Фазы 2. Поздние проходы Claude по всей ветке находят настоящие P1,
пропущенные первой итерацией; у Codex вне своих фиксов на поздних итерациях находок практически нет.

## Шаг 2. Ревью (итерация N)

`git status` чистый. `mkdir -p $RUN/iter-N`.

**Промпт роли** — короткий, всё общее уже в брифе:

```
Ревью только для чтения: код не правь и не коммить, исправления описывай, а не применяй. Не запускай
команд, меняющих рабочее дерево (git stash, checkout, reset) — параллельно работают другие ревьюеры.
Единственный файл, который ты пишешь, — файл замечаний ниже.

Прочитай бриф `<$RUN>/brief.md` (для spec-reviewer — `<$RUN>/brief-spec.md`) и работай по нему.

Итерация N, <Фаза 1 (Claude) | Фаза 2 (Codex): код прошёл ревью Claude-агентами, ищи то, что они
могли пропустить>.
Область: <вся ветка — `git diff <$BASE>...HEAD` | только эти изменения — `git diff <хэш>..HEAD`;
остальную ветку уже проверили>.
Приоритеты: <все | только P1 и P2>.
Замечания запиши в `<$RUN>/iter-N/<role>.md`.
```

**Claude-роли** — Agent tool, `subagent_type` = роль, все параллельно в одном сообщении. Дождись всех;
возврат каждой — одна строка, её и запоминай.

**Проверка read-only.** После возврата всех ролей (и в Фазе 2) — `git status --porcelain`. Перед ревью
дерево было чистым, а `.review/` игнорируется, значит любой вывод — правки ревьюера. Не откатывай их и
не принимай в итерацию: `git stash push --include-untracked -m "review iter N: правки ревьюера"`, строка
`⚠️ Итерация N: ревьюер изменил <файлы> — отложено в stash` в `$LOG` и в финальный отчёт, дальше по
циклу.

**Codex-роли** (Фаза 2) — тот же промпт, но последняя строка заменяется на «Файлы не пиши: замечания —
твоё финальное сообщение» (Codex работает в read-only песочнице). Агентов Claude Code Codex не видит,
поэтому роль передаётся текстом: в `$RUN/prompts/<N>-<role>.md` сначала тело файла агента `<role>.md`
(из `.claude/agents/` проекта или `~/.claude/agents/`) без frontmatter, затем промпт. Запусти все роли
параллельно, Bash tool с `timeout: 600000`:

```bash
codex exec --sandbox read-only --ephemeral --color never -C <repo> -o <$RUN>/iter-N/codex-<role>.md - < <$RUN>/prompts/<N>-<role>.md > <$RUN>/iter-N/codex-<role>.err 2>&1
```

Файл ответа не читай — его читает валидатор. По коду выхода:

- 0 и непустой файл ответа — файл идёт валидатору, если первая строка не `Замечаний нет` (проверь Grep-ом);
- ненулевой код или пустой файл ответа (технический сбой, таймаут, исчерпанная квота) — строка
  `CODEX_FAILED <role>, итерация N` в `$LOG`, остальные роли продолжают. Все роли итерации сбойные —
  Фаза 2 завершается с предупреждением «Фаза 2 не выполнена — сбой Codex»: к финальному отчёту. Пустые
  файлы сбойных ролей валидатору не отдавай — иначе сбой выглядит как схождение.

## Шаг 3. Валидация

Один **постоянный валидатор** на весь запуск, обе фазы. Он помнит, что уже отклонял и почему, поэтому
отсекает повторы — и поздних итераций Claude, и первой итерации Codex, которая поднимает отклонённое у
Claude. Валидация нужна всем ролям: по логам ревью она отклоняет 20–45% замечаний, и без неё цикл не
сходится — ревьюеры находят что-то почти на каждой итерации.

В задание итерации идут файлы ролей, чей возврат не `Замечаний нет` (для Codex — по Шагу 2). Таких нет
ни одной — валидатора не зови: итерация закрыта с нулём принятых, секцию `## Итерация N` с ролями и
«замечаний нет» допиши в `$LOG` сам.

- **Первое задание за запуск** (в любой фазе и итерации, в том числе в повторном запуске) — Agent tool,
  `subagent_type: "general-purpose"` без `model` (модель сессии: судье нужна модель сильнее
  ревьюеров-sonnet), промпт из [references/validator-prompt.md](references/validator-prompt.md) с
  подставленными путями и заданием итерации. Запомни его ID.
- **Дальше** — SendMessage этому же агенту:

```
Итерация N, <фаза>. Файлы замечаний: <список>. Приоритеты: <все | только P1/P2>.
Область: <вся ветка | git diff <хэш>..HEAD>.
```

Валидатор пишет секцию итерации в `$LOG`, список к исправлению — в `$RUN/iter-N/accepted.md`,
`[escalation]` — в `$EXEC_LOG`, и возвращает до шести строк. Покажи их пользователю как есть; строка
«Роли с принятыми» задаёт состав следующей итерации.

Агент недоступен (упал, SendMessage вернул ошибку) — запусти свежего с тем же первым промптом: история
лежит в `$LOG`, он дочитает её сам.

## Шаг 4. Исправление и коммит

Исправлять нечего — к Шагу 5. Есть — **постоянный фиксер**, тот же принцип: он помнит, что уже правил.

- **Первое задание за запуск** — Agent tool, `subagent_type: "general-purpose"`, `model: "sonnet"`,
  промпт из [references/fixer-prompt.md](references/fixer-prompt.md). Запомни его ID.
- **Дальше** — SendMessage: `Итерация N, <фаза>: исправь <$RUN>/iter-N/accepted.md.`

Фиксер правит, гоняет тесты и линтер, коммитит и дописывает в `$LOG` секции `### Исправления` и
`### Коммит`. Возвращает хэш коммита, счёт «исправлено K из M» и нерешённое — нерешённое покажи
пользователю. Дальше:

- K > 0 — проверь `git status` (чистый) и `git log -1 --oneline` (коммит итерации есть). Не так — один
  SendMessage фиксеру с тем, что не так. Не помогло — финальный ответ `FAILED` («фиксер не довёл
  итерацию N до коммита»).
- K = 0 — коммита нет и не должно быть; нерешённое остаётся в `$LOG`. Фаза завершается: ревьюеры снова
  поднимут те же замечания, а исправить их фиксер не может. В `$LOG` строка «Фаза завершена: фиксер
  не смог исправить принятое».

## Шаг 5. Решение

Проверь Grep-ом: секция `## Итерация N` в `$LOG` есть; при исправленных — `### Исправления` и
`### Коммит`; `git status` чистый. Чего-то нет — вернись и доделай.

- Принятых к исправлению на этой итерации 0 → фаза завершена.
- Итераций в фазе 5 → фаза завершена по лимиту, строка в `$LOG`.
- Фаза 1 завершена → `### Фаза 1 (Claude) завершена: K итераций, PHASE2_BASE <хэш HEAD>` в `$LOG` и Фаза 2
  (или финальный отчёт, если Codex отключён). Фаза 2 завершена → финальный отчёт.
- Иначе `N + 1`, состав по строке «Роли с принятыми» валидатора и таблице итераций, Шаг 2.

## Финальный отчёт

SendMessage валидатору: «Ревью завершено, HEAD <хэш>. Допиши в `$LOG` секцию `## Итог` и верни её
сжатой.» Формат секции — в его промпте. Валидатор не запускался ни разу (замечаний не было) — секцию
напиши сам по тому же формату, она короткая; строка `- **HEAD:**` обязательна — по ней повторный
запуск находит свою базу.

**Автономный режим** — финальный ответ не длиннее 15 строк, ничего сверх контракта:

```
DONE | BLOCKED | FAILED
<итог в 3–5 строк: итерации Ф1/Ф2, принято/отклонено, число коммитов, что осталось>
[escalation] review: <суть> — <между чем выбор>      (каждая строкой, или «эскалаций нет»)
Кандидаты в бэклог: <N — в $LOG, секция «Итог»>
Лог: $LOG
```

`FAILED` — цикл не довёл итерацию до коммита. `BLOCKED` — продолжать нельзя без решения пользователя
(грязное дерево на старте, неразрешимая эскалация, мешающая идти дальше).

**Ручной запуск** — покажи пользователю итог валидатора, предложи завести кандидатов в бэклог и закончи строкой `Полный лог ревью: $LOG`.
