# st-ticket-workflow: живой лог работы по Jira-тикету

Дока `docs/tickets/<KEY>.md` живёт в репозитории, где идёт работа, и служит общей памятью между агентами
и сессиями: отброшенные подходы, worktree в смежных репо, ответы на блокеры, отложенное «до мержа».
Без неё следующий агент повторит пройденный путь. Каждое существенное событие оставляет след в доке к концу
подзадачи или сессии — особенно если подход не сработал.

Этот файл — ядро. По ссылке из него читаются:

- `init.md` — процедура `init` целиком (ветка, каркас, контекстная карта, оценка требований, коммит);
- `migration.md` — миграция в директорию и дробление, когда точка входа ≥ 500 строк;
- `template.md` — шаблон файла, порядок секций фиксирован.

Ключа в ветке нет — дока не ведётся, про тикет не спрашивать.

## Параметры

`$ARGUMENTS`: первое слово — Jira-ключ, второе — режим `init` (создать; ошибка, если есть), `update`
(записать; ошибка, если нет), `read` (прочитать и пересказать). Без режима: нет файла → `init`, есть →
`update`. Ключ не передан — взять из имени ветки; не определился — спросить через
AskUserQuestion. Без ключа скилл не работает.

Ключ из ветки: сегмент после последнего `/`, в его начале `<буквы>-<цифры>`, буквы в верхний регистр.
`feature/proj-123-add-login` → `PROJ-123`; `refactor/db-layer`, `master` → ключа нет.
Извлечённый ключ подтверди одной строкой: «Определил тикет из ветки `<branch>` → `<KEY>`. Продолжаю.»

## Шаг 1. Локализация файла

Относительно корня текущего чекаута (для worktree — сам worktree):

- есть `<KEY>.md` → точка входа; директория `<KEY>/` без `index.md` рядом — хранилище артефактов;
- нет `<KEY>.md`, есть `<KEY>/index.md` → точка входа `index.md`;
- есть оба → конфликт: сообщить пользователю, оставить один вход;
- нет ни того, ни другого → сначала проверить, не лежит ли дока вне ветки: untracked
  в основном чекауте того же репо → перенести в ветку и закоммитить; в соседнем репо →
  вести там, текущий worktree добавить в её `worktrees:`. Найдена — `init` не делать;
- нет нигде → `init`;
- файл в чужом формате (нет frontmatter и `## Текущий статус`) → адопция:
  при первом обновлении добавить сверху frontmatter и `## Текущий статус`, `## Задачи`, `## Лог работы`,
  существующее оставить ниже, в лог — «дока адоптирована».

## Шаг 2. `init`

Прочитай `init.md` целиком и выполни. Это разведка в три прохода (каркас → контекстная карта → оценка
требований) плюс коммит; начинается с гейта ветки: на `master`/`main`/`develop` init сначала уводит
сессию в worktree, иначе доку некуда коммитить.

## Шаг 3. Чтение (`read` и обязательный пред-шаг `update`)

Прочитать файл целиком, включая лог; директория — `index.md` целиком плюс `ls docs/tickets/<KEY>/`.
Сверить с реальностью: `branch` во frontmatter против `git branch --show-current`, пути `worktrees`
существуют, секция `## Задачи` есть (legacy `## Чек-лист` → миграция ниже) и открытые пункты актуальны.
Расхождение — обновить frontmatter и записать в лог. `branch` — рабочая ветка тикета: follow-up ветка по
уже влитой работе (догоняющая дока, итог деплоя) расхождением не считается и его не меняет.

## Шаг 4. `update`

| Событие | Что обновить |
|---|---|
| отложенная задача: реплика пользователя «потом / не забыть / перед мержом», решение агента отложить, незакрытое замечание ревью | пункт в `## Задачи`, в тот же ход |
| пункт выполнен | `[x]`, в тот же ход |
| завершена подзадача | запись в логе, `[x]`, при необходимости «Текущий статус» |
| принято архитектурное решение | `## Решения` + запись в логе |
| отброшен подход | запись в логе с «почему» + строка-индекс в `## Отброшенные подходы` |
| блокер / открытый вопрос | `## Open questions / Blockers`, при необходимости `status: blocked`; держит мерж → пункт в «До мержа» |
| ответ на блокер | убрать оттуда, суть в `## Решения` или лог, обновить `status` |
| worktree в смежном репо | `worktrees` во frontmatter + лог |
| новая ссылка на wiki / RFC / смежный тикет / тред | `## Контекстная карта` (выжимка по источнику) или Reading guide + лог |
| работа тикета переехала в другую ветку (не follow-up по влитой) | `branch` во frontmatter + лог |
| конец сессии при незавершённой работе | «Текущий статус», чтобы следующий агент сразу понял, где мы |

**Запись лога**: `### YYYY-MM-DD — короткое описание` (`date +%F`, без времени), в конец `## Лог работы`,
3–10 строк: что сделано, что выяснилось, выводы. Отброшенный подход — обязательно почему: что сломалось,
какое наблюдение привело к решению.

**Фильтр записи**: попадает только то, что относится к нашей ветке и пригодится следующему агенту по этой
задаче. Открыл лог через две недели — поможет? Нет — выкинь. Отсюда:

- никаких «попутно заметил в master» и находок из чужих веток; влияет на нас — одна строка про последствие;
- никаких гипотез и «возможно»: факты в лог, допущения (уверенность ≥ 90 %) в `## Допущения`, вопросы —
  в `## Open questions / Blockers`;
- никаких ритуальных метрик: `N passed`, имя бэкап-ветки, хеши до/после force-push. Число пишется, только
  если оно само вывод («после rebase упали 3 теста из-за Y»); чистый rebase и зелёные тесты — одной строкой;
- контекст события — минимум, без которого вывод непонятен; разбор, полезный в момент решения, идёт
  в `## Решения` или не сохраняется;
- никаких списков коммитов (хеши, заголовки): git переписывается при rebase/squash, и ссылки протухают.
  Описывай суть изменений, не их упаковку. Исключение — коммит уже в защищённой ветке, на который
  ссылаются извне;
- свой MR не записывается ни ссылкой, ни записью «MR заведён»: он восстанавливается по ветке
  (`glab mr list --source-branch`). Чужие MR, на которые опирается работа, — ресурсы контекстной карты.

Сомневаешься — короче. Лог легко наращивать, тяжело вычищать.

**Текущий статус** — 1–3 строки «где мы», перезаписывается целиком. Формулировать так, чтобы текст остался
верным после мержа открытого MR: описывать состояние target после мержа, «ещё не влито» выражать через
`## Задачи`. Свежий агент за 30 секунд должен понять, где мы.

## Шаг 5. Миграция по размеру

Перед записью в `update` — `wc -l` точки входа. ≥ 500 строк → `migration.md`. `## Текущий статус` и
`## Задачи` всегда остаются в `index.md`: по ним следующий агент первым делом понимает, где мы.

## Задачи — трекер по тикету

Секция сразу после `## Текущий статус`. Лог — что произошло, Задачи — что предстоит.

```markdown
## Задачи

### До мержа
- [ ] добавить тест на пустой ответ keys-API — ревьюер просил в !412
- [x] ~~обновить README по флагу~~ — отменено 2026-08-19: флаг убрали (см. Решения)

### После мержа
- завести follow-up тикет на рефакторинг Y — перенесено из «До мержа» 2026-08-19: не тащим в этот MR

### Отложено / идеи
- [ ] кэшировать ответ Z (заметил по ходу)
```

Группы: **До мержа** — всё, без чего MR нельзя вливать; группа по умолчанию; только её считает гейт.
**После мержа** — деплой, наблюдение, follow-up; пункты без чекбоксов: после мержа доку уже не правят,
отмечать сделанное некому. **Отложено / идеи** — необязательное; стало
обязательным → в «До мержа». **Не разобрано** — только для мигрированных legacy-пунктов, в новых доках
не создаётся, гейт её игнорирует; пустеет — заголовок удалить.

Правила пунктов:

- `- [ ] что сделать — контекст одной строкой` (в «После мержа» — `- что сделать`); новые в конец
  группы; без приоритетов и дат.
- Пункт — работа с кодом, данными или системами тикета. Шаги личного процесса автора (итоговый коммент
  и закрытие тикета в Jira, уборка worktree, worklog, бэклог) в доку не пишутся.
- «Что сделать» — проверяемый критерий, который требует всей работы: «каждый вызов `fetch_keys`
  обёрнут в ретрай», а не «разобраться с ретраями». Размытый пункт закрывается раньше, чем сделан,
  а гейт видит `[x]`, а не работу.
- Сделано → `[x]` в тот же ход, строка остаётся до финала тикета.
- Перенос из «До мержа» или отмена — только с согласия пользователя, с хвостом `— перенесено из
  «До мержа» <дата>: почему` или `~~текст~~ — отменено <дата>: почему` (и `[x]`). Обратный перенос —
  сам.
- Блокер, который держит мерж, дублируется пунктом в «До мержа». Перед добавлением — проверка на дубль.
- TodoWrite умирает с сессией, план `docs/plans/*` построчно не дублируется: в «До мержа» один пункт
  «выполнить план <путь>» плюс то, что всплыло вне плана.

**Захват в тот же ход**, без слова «запиши», с подтверждением в ответе `📌 В задачи (До мержа): <текст>`.
Источники: реплика пользователя с отложенным намерением («не забыть», «потом», «перед мержом», «ещё
надо», «TODO», «follow-up», «после деплоя», «добавь тест на…»; группа по смыслу реплики); собственное
решение агента отложить («разберусь позже», «пропускаю», «временный хак», «не стал трогать») — отложить
без следа нельзя; внешние замечания (ревью MR, `st-review`, `st-manual-test`, комментарии в Jira), не
исправленные сразу.

**Целевое время доков** — обязательный пункт «До мержа», заводится при `init`, не удаляется. Ветка
умирает при мерже, поэтому всё, что дока утверждает после мержа, пишется до него: состояние кода и конфига
в настоящем времени, без «пока выключено», «после деплоя», «чтобы включить — сделай». Граница — код и
конфиг, не рантайм: «выкачено в кластер» живёт только в логе и дописывается постфактум. Закрывается
перечнем проверенного (`[x] … — проверены docs/usage.md, CLAUDE.md, «Текущий статус»`), не пустой
галочкой; переоткрывается на каждый следующий MR по тикету. Кандидатов даёт `st-branch-finalize` по
диффу; страницы, которые обязаны были измениться и не изменились, — на совести агента.

**Гейт.** Пока в «До мержа» есть открытые пункты, финализация (`st-branch-finalize`, `st-mr-create`,
`glab mr merge|create` кроме `--draft`) не запускается. Пользователь намекает на финал («давай MR»,
«вливаем», «сворачиваемся») → до вызова показать открытые пункты и согласовать: сделать / перенести
(куда, почему) / отменить. Субагент, упёршийся в гейт, доку не правит — возвращает список родителю.

**Legacy** `## Чек-лист` при первом обновлении: переименовать в `## Задачи`, все старые пункты в
`### Не разобрано`, добавить пустые три группы, перенести под `## Текущий статус`, строка в лог. Разбор —
вместе с пользователем при ближайшем касании.

## Перед завершением сессии, переключением задачи или MR

1. «Текущий статус» переписан: понятен за 30 секунд и верен после мержа открытого MR.
2. Отброшенное — в логе с «почему» и строкой в `## Отброшенные подходы`; решения — в `## Решения`.
3. Блокеры — в `## Open questions / Blockers`; отвеченные убраны; при изменении состава — пересмотреть
   `## Оценка требований`.
4. `## Задачи`: сделанное `[x]`, отложенное за сессию добавлено, в «До мержа» нет уже сделанного;
   пункт целевого времени доков закрыт перечнем проверенного. Перед финализацией «До мержа» пусто либо
   перенесено с согласия пользователя — иначе гейт не пройден.
5. Frontmatter (ветка, worktrees, статус) актуален; новые источники за сессию — в `## Контекстная карта`
   выжимкой; подтверждённые или опровергнутые допущения отмечены.
6. Запись в `## Лог работы` и коммит `docs(<KEY>): <событие>` (можно вместе со связанным кодом).

Ничего не изменилось — доку не трогать.

## Правила ведения

- Дока коммитится сразу после init и каждого существенного обновления: незакоммиченная не видна в linked
  worktree, и агент там заводит вторую.
- Субагенты доку не редактируют — возвращают задачи и решения родителю.
- Секреты и токены в доку не попадают; в логах — маскировать.
- Большие куски кода и описаний из Jira не копировать: дока — навигатор, цитата на 5 строк уместна, на
  100 — ссылка.
- Старые записи лога не редактировать (кроме опечаток и ссылок); устарело — новая запись «Пересмотр…».
- Факт, записанный в логе и в `## Решения`, в индексе повторяется одной строкой.
- Артефакты в директории тикета — kebab-case с датой спереди: `2026-05-10-prod-logs-dump.txt`.

## Что скилл не делает

Не закрывает тикет, не создаёт MR (`st-mr-create`), не пишет план
(`st-plan-create`), не пишет worklog в Jira, не запускает CI и тесты. Нужны другие действия —
вызови соответствующий скилл, в доке зафиксируй факт и результат.
