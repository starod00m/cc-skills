# st-ticket-workflow — режим `init`

Читается из `SKILL.md` только в режиме `init`. Шаблон файла — `template.md`.

Init — разведочный этап, а не «создать файл из шаблона»: к его концу агент понимает тикет глубже
постановщика, иначе следующие сессии бегают по тем же ссылкам и упираются в те же блокеры. Четыре прохода,
ни один не пропускается: **2.0 ветка → 2.1 каркас → 2.2 контекстная карта → 2.3 оценка требований →
2.4 коммит**. Перед init убедись, что доки нет ни в ветке, ни в основном чекауте, ни в
соседнем репо — иначе это перенос или адопция (SKILL.md, шаг 1).

## 2.0 Ветка до файлов

Init завершается коммитом, а коммит в `master`/`main`/`develop` запрещён;
файл, созданный на дефолтной ветке, остаётся untracked в основном чекауте, а в worktree заводится вторая
копия.

1. `git branch --show-current`.
2. Ветка не дефолтная → к 2.1. Сессия уже в worktree (`git rev-parse --git-dir` и
   `git rev-parse --git-common-dir` не совпадают) → тоже к 2.1, worktree в worktree не вкладывать.
3. Ветка дефолтная → worktree до создания файла, без вопроса пользователю: имя ветки — семантический
   префикс (`feat/`, `fix/`, …) плюс ключ и slug, например `feat/proj-123-add-login` (пример
   конвенции — замени на свою); создать через `EnterWorktree` (не `git worktree add`); сказать
   пользователю, какая ветка и worktree созданы, и продолжить init внутри.

Режимов `read` и `update` гейт не касается.

## 2.1 Каркас

```
mcp__jira__jira_get_issue issue_key=<KEY> fields="summary,description,status,priority,labels,components,parent,issuelinks,attachment" comment_limit=50
```

`comment_limit=50`: в комментариях часто лежат уточнения требований и ссылки на смежные ресурсы.

`mkdir -p docs/tickets`, создать `docs/tickets/<KEY>.md` по `template.md`:

- `jira_key`, `title` (= `summary`), `jira_url` (`https://<jira-host>/browse/<KEY>`, хост из ответа MCP
  или существующих ссылок репо), `status: in-progress` (2.3 может сменить на `blocked`), `branch`
  (текущая, если не дефолтная), `related_tickets` (ключи из `issuelinks`), `worktrees: []`;
- `## Контекст` — 3–5 строк «что делаем и зачем» из `description`, не копия;
- `## Задачи` → `### До мержа`: первым — обязательный пункт «доки описывают состояние ПОСЛЕ мержа»
  (формулировка в `template.md`), он про сверку, а не про наличие диффа; дальше известные подзадачи;
  плана ещё нет — пункт «составить план реализации». Группы «После мержа» и «Отложено / идеи» —
  пустые заголовки. «Не разобрано» не создаётся;
- первая запись лога с сегодняшней датой — «Заведена дока, тикет взят в работу».

## 2.2 Контекстная карта

Контекст задачи размазан по Mattermost, Confluence, GitLab и смежным тикетам. Цель — собрать все точки
в одну карту с выжимками: не пересказ, а что важного оттуда узнали для этой задачи.

Откуда брать ссылки: `description`, все комментарии, `issuelinks`, `parent`/эпик, `attachment`.

| Источник | Как читать | Что выписать |
|---|---|---|
| Mattermost (ссылки вида `…/pl/*`, `…/messages/*`) | MCP `mattermost` (`get_thread`, `get_channel_messages`), не браузером | тема, договорённости, кто решил, дата |
| Confluence | MCP `confluence` (`confluence_get_page`, `confluence_get_page_outline`) | заголовок, требования и ограничения, актуальна ли страница |
| смежные Jira-тикеты (issuelinks, `PROJ-NNN` в тексте) | `jira_get_issue` | как связан (предшественник / блокер / часть эпика / дубликат), статус, выводы |
| GitLab MR, коммиты, issues | `glab` | назначение, target, влит ли, важные замечания ревью |
| эпик / родитель | `jira_get_issue` | бизнес-цель верхнего уровня |
| аттачменты Jira | `mcp__jira__jira_download_attachments`, если критично | что в файле, чем полезен |
| внешние ссылки (Notion, Google Docs) | `WebFetch`, если доступно | недоступно → в Open questions: «внешний документ, нужен доступ» |

2–5 строк на источник. Не угадывать содержимое по URL: либо прочитал и записал факт, либо «не смог
прочесть» с причиной. Из тикета A ссылка на B — B прочитать; дальше по ссылкам из B — только если они
названы важными для нашей задачи.

Записать в `## Контекстная карта` по `template.md`. По типу источника ничего не нашлось — явно
«не обнаружено», чтобы следующий агент видел: проверено, а не забыто.

## 2.3 Оценка полноты требований

Единственный шаг init, который может развернуть работу на «сначала спроси». Цель — отделить то, что
можно делать, от того, что без уточнения сделается мимо ожиданий.

| Категория | Признак | Что делать |
|---|---|---|
| **Блокер** | без ответа реализация невозможна или гарантированно пойдёт не туда; из контекста не выводится | Q-пункт в `## Open questions / Blockers` с адресатом; `status: blocked`; держит мерж → пункт в «До мержа» |
| **Средний** | можно додумать с уверенностью ≥ 90 % | строка в `## Допущения`: «<что предположили>. Источник догадки: <почему уверены>»; подтвердить при первом ревью |
| **Минор** | хорошо бы знать, влияние маргинальное | одной строкой в init-записи лога: «Минор: хотелось бы X, не критично» |

Мысленный чек-лист (в доку не выводить): какой конкретный результат нужен и по какой метрике; на каких
входах и окружениях; кто приёмщик и по какому критерию; есть ли зависимости от других команд, релизов,
флагов; не противоречит ли тикет контекстной карте.

Записать в `## Оценка требований` по `template.md`, включая явные «не выявлено» по каждой категории.
При блокерах — в конце init короткое уведомление в чат без AskUserQuestion: «Выявил N блокеров,
требующих уточнения до начала реализации: <по строке каждый>». Пользователь решит, выяснять сейчас или
идти с допущениями.

## 2.4 Коммит

```bash
git add docs/tickets/<KEY>.md        # или docs/tickets/<KEY>/ при директории
git commit -m "docs(<KEY>): заведена дока тикета"
```

Сразу, не откладывая: linked worktree не видит untracked-файлов основного чекаута.
