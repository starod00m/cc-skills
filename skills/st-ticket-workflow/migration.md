# st-ticket-workflow — миграция доки в директорию и дробление (шаг 5)

Читается из ядра `SKILL.md`, когда точка входа доки переросла порог (см. триггер ниже).

## Триггер

Перед записью в режиме `update` посчитать размер точки входа (либо `docs/tickets/<KEY>.md`, либо `docs/tickets/<KEY>/index.md` — что есть):

```bash
wc -l "$TICKET_FILE"
```

Если строк ≥ 500 — нужна **миграция в директорию (если ещё не сделана) + дробление контента**. Просто переименовать `<KEY>.md` в `<KEY>/index.md` без дробления — бессмысленно: index.md остаётся таким же тяжёлым, читать его в следующих сессиях так же дорого. Цель шага — уменьшить index.md до состояния «беглый обзор за минуту», вынеся объёмные логические разделы в отдельные файлы рядом.

Триггер работает и для уже мигрированной директории: если `index.md` после миграции снова перерос 500 строк (или мигрировали ранее без дробления), всё равно проходим шаги ниже. В этом случае шаг 5.1 пропускается (директория уже есть), сразу идём в 5.2.

## 5.1 Перевести layout в директорию

```bash
mkdir -p "docs/tickets/${KEY}"
git mv "docs/tickets/${KEY}.md" "docs/tickets/${KEY}/index.md"
```

(Если репо не git — обычный `mv`.) Если директория `docs/tickets/<KEY>/` уже существовала как хранилище артефактов (без `index.md`) — это штатно: `index.md` просто добавляется к ним.

## 5.2 Дробление index.md по логическим разделам

После перевода в директорию **сразу же** разнести крупные секции в отдельные файлы. Каждый вынесенный файл лежит рядом с `index.md`, в `index.md` остаётся короткая ссылка-карточка (1–3 строки: о чём раздел + ссылка).

Кандидаты на вынос (в порядке приоритета):

| Секция в index.md | Куда выносить | Когда выносить |
|---|---|---|
| `## Лог работы` | `log.md` | Почти всегда — лог пухнет быстрее всего |
| `## Решения` | `decisions.md` | Если ≥3 решений или ≥80 строк |
| `## Отброшенные подходы` | `rejected.md` (или вместе с решениями в `decisions.md`) | Если ≥5 пунктов |
| Длинные пост-деплой инструкции (из `### После мержа` или отдельной секции) | `post-deploy.md` | Если ≥50 строк суммарно; в `### После мержа` остаётся пункт-ссылка |
| `## Контекстная карта` | `context-map.md` | Если ≥80 строк или там много выжимок из Confluence/Mattermost |
| Большие куски Reading guide / Связанных ресурсов | обычно остаются в index.md | Выносить редко, они и так короткие |

`## Текущий статус`, **`## Задачи`**, `## Reading guide`, `## Контекст`, `## Open questions / Blockers`, frontmatter — **всегда остаются в index.md**. Это «панель приборов», по ней следующий агент за 30 секунд понимает где мы. **`## Задачи` не выносить никогда**: по ней проверяется гейт финализации (SKILL.md, «Гейт») — вынесенную секцию легко пропустить.

## 5.3 Формат ссылок-карточек в index.md

После выноса секции — на её месте в index.md остаётся короткая карточка-указатель. Не пустая ссылка, а 1–3 строки, чтобы из index.md был понятен **состав** вынесенного без открытия файла. Примеры:

```markdown
## Лог работы

См. [log.md](log.md) — хронологический лог работы по тикету (последняя запись: 2026-05-13 — закрыты Q5/Q6 ответом аналитика).
```

```markdown
## Решения

См. [decisions.md](decisions.md). На текущий момент: 4 решения (схема хранения, scope отчёта, ответы аналитика по краевым случаям). Отброшенные подходы — там же.
```

```markdown
### После мержа
- выполнить пост-деплой по [post-deploy.md](post-deploy.md) (миграции, бэкфилл данных, обновление дашборда)
```

## 5.4 Правила выноса

- **Один файл — один логический раздел.** Не сваливать «всё длинное» в один `misc.md` — теряется навигация.
- **Frontmatter в дочерних файлах не нужен.** Frontmatter только у `index.md` — он остаётся точкой входа.
- **Внутренние перекрёстные ссылки между файлами** — относительные (`[см. Решение 2](decisions.md#решение-2)`). После выноса пройтись по index.md и заменить старые внутренние якоря на ссылки в вынесенные файлы.
- **Артефакты (скрины, дампы, SQL-черновики)** — складываются туда же, в директорию тикета, с осмысленными именами и датой-префиксом (`2026-05-13-qa-test-plan.md`). Это отдельный механизм, **не путать** с дроблением контента: артефакты — внешние материалы, дробление — разделение самого журнала задачи.
- **`## Задачи` остаётся в index.md** (см. 5.2).

## 5.5 После миграции

- В лог (`log.md` если уже вынесен, иначе в `## Лог работы` index.md) — запись о миграции и составе вынесенных файлов.
- Пробежаться по ссылкам внутри текста: пути относительно index.md теперь на одну директорию глубже корня репо, относительные пути к коду (`schema/...`, `tests/...`) **не меняются** (рендерятся всё равно от корня).
- Если в директории уже жили артефакты, скопившиеся до миграции — оставить их на месте.
- Закоммитить: `docs(<KEY>): миграция доки в директорию`.

## 5.6 Когда повторно дробить

Если после уже выполненной миграции какой-то из вынесенных файлов (например, `log.md`) сам по себе перевалил за ~500 строк — резать его уже **по событиям**, не по строкам:

- Длинный отчёт ручного QA из лога → `2026-05-12-manual-qa-report.md`, в логе остаётся однострочная карточка со ссылкой.
- Длинный SQL-разбор / план миграции → отдельный файл с датой в имени.

index.md повторно дробить уже не нужно — он после первой миграции живёт в режиме «панель приборов» и расти не должен.
