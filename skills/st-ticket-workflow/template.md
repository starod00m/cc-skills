# st-ticket-workflow — шаблон доки `docs/tickets/<KEY>.md`

Используй ровно эту структуру при `init`. **Порядок секций фиксирован** — следующий агент полагается на него при беглом сканировании.

```markdown
---
jira_key: PROJ-123
title: Краткий заголовок тикета
jira_url: https://<jira-host>/browse/PROJ-123
status: in-progress  # in-progress | blocked | review | done
branch: feat/proj-123-feature-name
related_tickets:
  - PROJ-120
  - PROJ-130
worktrees: []
# worktrees:
#   - repo: name-of-repo
#     path: ../other-repo/.worktrees/proj-123
#     branch: feat/proj-123-...
---

# PROJ-123 — Краткий заголовок тикета

## Текущий статус

Одна-три строки: где мы сейчас, в состоянии target после мержа (правила — SKILL.md, «Текущий статус»).

## Задачи

Правила групп, захвата и переносов — SKILL.md, «Задачи — трекер по тикету».

### До мержа
- [ ] **доки описывают состояние ПОСЛЕ мержа** — usage/README/CLAUDE.md и «Текущий
      статус» этой доки не утверждают того, что мерж отменит. Вердикт — шаг «доки» в
      `/st-branch-finalize`; закрывать перечнем проверенного
- [ ] подзадача, без которой MR нельзя вливать — контекст одной строкой (опционально)
- [x] сделанная подзадача (остаётся до финала тикета)

### После мержа
- деплой / post-deploy проверка / follow-up (без чекбокса)

### Отложено / идеи
- [ ] необязательное; станет обязательным → переезжает в «До мержа»

## Reading guide

Что обязан прочитать новый агент перед началом работы.

**MUST READ (всегда, до первого действия):**
- Этот файл целиком (включая весь лог).
- Сам тикет в Jira: PROJ-123.
- <ключевые файлы реализации, по мере появления>

**READ ON DEMAND (только при необходимости):**
- <ссылка> — <когда читать: "если возник вопрос про X">
- <wiki-страница> — <когда читать>
- <смежный тикет / RFC / MR> — <когда читать>

## Контекст

Краткое (3–5 строк) изложение задачи: что делаем и зачем. Выжимка, не копия description.

## Контекстная карта

Сводка по всем источникам контекста, найденным при init (init.md, шаг 2.2). По каждому источнику: 2–5 строк выжимки + ссылка на оригинал. Если по типу источника ничего не нашли — явная запись «не обнаружено», чтобы следующий агент видел: проверено, а не забыто.

### Jira (issuelinks, эпик, родитель)

- **PROJ-120** (предшественник, Done): кратко что было сделано и как связано с нашей задачей. [ссылка]
- **PROJ-200** (эпик, In progress): бизнес-цель верхнего уровня. [ссылка]

### Mattermost

- Тред в `#channel-name` от YYYY-MM-DD: краткая суть обсуждения, ключевая договорённость, кто решил. [ссылка]
- Или: «Обсуждений в Mattermost не обнаружено».

### Confluence

- «Название страницы» (актуальна / устарела): что важного для задачи. [ссылка]
- Или: «Confluence-страниц не обнаружено».

### GitLab (MR / коммиты / issues)

- MR !123 (merged YYYY-MM-DD): что вливал, target branch, ключевые замечания ревью. [ссылка]
- Или: «Связанных MR не обнаружено».

### Аттачменты и внешние документы

- `spec-v2.pdf` (приложение к тикету): краткая суть, ключевые требования. [путь, если скачан]
- Внешняя ссылка `notion.so/...` — недоступна агенту, нужен доступ. (если применимо)
- Или: «Аттачментов и внешних документов не обнаружено».

## Оценка требований

Результат init 2.3: достаточно ли собранного контекста для корректной реализации задачи. Секция обязательна, даже если всё чисто — следующий агент должен видеть, что оценка проводилась.

### Блокеры (реализация невозможна без уточнения)

- Или конкретные пункты — каждый дублируется в `## Open questions / Blockers` с указанием адресата.
- Или явная фраза: «Блокеров не выявлено».

### Средние (можно додумать с уверенностью ≥90%)

- Перечислены в `## Допущения` с краткой формулировкой и обоснованием догадки.
- Или: «Средних расхождений не выявлено».

### Миноры (хорошо бы, но и без этого справимся)

- Перечислены одной строкой каждый, без отдельной секции под них.
- Или: «Миноров не выявлено».

## Допущения

Принятые догадки уровня «среднее» из оценки требований. Каждое допущение — одной строкой: что предположили + почему уверены. Допущения подлежат подтверждению при первом ревью; после подтверждения переезжают в `## Решения`, после опровержения — порождают запись в логе и при необходимости откат.

- (пусто, если допущений нет)

## Open questions / Blockers

Открытые вопросы, ждущие ответа. Каждый пункт — отдельный блокер с пометкой «к кому обращён».

- [ ] **Q1 (к @reviewer):** формулировка вопроса. *Зачем знать:* что именно зависит от ответа.
- [ ] **Q2 (к аналитику):** ...

При получении ответа — пункт удаляется отсюда, ответ переносится в `## Решения` или лог. Блокер, который держит мерж, дополнительно дублируется пунктом в `## Задачи` → `### До мержа`.

## Решения

Принятые решения с пояснением. Дополняет «Отброшенные подходы»: тут — что **выбрали**, там — что **отбросили**.

### YYYY-MM-DD — Решение N

Краткая формулировка: «Выбрали X вместо Y, потому что Z».
Контекст / последствия — 1–3 строки.

## Отброшенные подходы

Короткий индекс отвергнутых путей. У каждого пункта — ссылка на запись лога с подробностями (почему, что наблюдали).

- **Подход A** — отброшен YYYY-MM-DD. Кратко: причина одной строкой. Подробности: см. лог [YYYY-MM-DD — заголовок записи](#yyyy-mm-dd--заголовок-записи).
- **Подход B** — отброшен YYYY-MM-DD. ...

## Связанные ресурсы

Хранилище ссылок, которые не классифицируются как «обязательные» / «по необходимости» (это в Reading guide), но полезны.

- MR: <ссылка>
- Worktrees: см. frontmatter `worktrees`.
- Смежные тикеты: см. frontmatter `related_tickets`.
- Wiki: <ссылки на локальную wiki>
- Документы: <RFC / спеки / Confluence>

## Лог работы

Прямой хронологический порядок. Новые записи добавляются **в конец**.

### YYYY-MM-DD — Заведена дока, тикет взят в работу

Стартовая запись.
```
